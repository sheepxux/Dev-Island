# Dev Island Software Bill of Materials

Every reviewed Release is designed to publish `Dev-Island.spdx.json`, a
deterministic SPDX 2.3 software bill of materials generated by the repository's
own `scripts/release/generate-sbom.swift` tool.

## Inventory boundary

The SBOM contains:

- the Dev Island product version and tagged Git revision;
- every exact SwiftPM version and 40-character Git revision from
  `Package.resolved`;
- the vendored toml++ version parsed from the exact header compiled through
  swift-toml;
- all nine Agent brand sources and the exact 18 PNGs shipped at 1×/2× density,
  including each source SVG SHA-256, packaged PNG SHA-256, asserted upstream
  revision/path/SHA-256 and closed transform, license assertion, bundled
  notice SHA-256 and human provenance/trademark review state; and
- relationships from Dev Island to its locked Swift packages and from
  swift-toml to toml++, plus one `CONTAINS` relationship from Dev Island to
  every shipped Agent brand asset set.

The current v0.3.0 inventory contains 38 components: Dev Island, 27 SwiftPM
pins, toml++ 3.4.0, and nine Agent brand asset sets.

Generation reads the license notices from the already packaged App. Every
locked repository must have a non-empty bundled `LICENSE`/`COPYING` notice;
toml++, Lobe Icons, Primer Octicons, OpenCode, Kimi Code, Qwen Code and Dev
Island must have their dedicated notices. Brand manifest schema v3 also pins
the exact bytes of every notice. The
generator reads the reviewed brand manifest, all source SVGs, and the actual
PNG bytes inside the built App; any missing, extra, symbolic-link, or hash-
drifted asset fails. A missing or unrepresented notice also fails the build.
This keeps the SPDX inventory, lock file, compiled vendored header, shipped
brand bytes and attribution directory in one release boundary.

Dependencies conservatively use `NOASSERTION` for declared/concluded licenses;
the SBOM is an exact component inventory, not a legal opinion. Dev Island, the
directly inspected toml++ header, the reviewed OpenCode asset, the five exact
Lobe Icons sources and the adapted Primer Octicons source declare MIT. The
Kimi VS Code subproject asset and Qwen Desktop Shell asset declare Apache-2.0
from their exact pinned upstream license boundaries. The full source notices in
`Contents/Resources/ThirdPartyLicenses` remain authoritative attribution copy.

The SBOM records review state but does not approve it. The tagged Release gate
stops before credentials are loaded while any manifest entry still requires
provenance or trademark review. See `docs/BRAND_ASSET_REVIEW.md`.

## Reproducibility and trust

The document timestamp comes from the tagged Git commit's source-date epoch,
not wall-clock generation time. Package order, relationships, JSON keys, and
formatting are deterministic. The namespace binds product version, Git
revision, and SHA-256 of `Package.resolved`; a second `--check` invocation must
reproduce the document byte for byte.

That lock file also controls compilation rather than serving only as SBOM
metadata. PR and tagged Release workflows reject an untracked, missing, or
linked `Package.resolved`; full tests and both Universal App architecture
builds use SwiftPM's force-resolved mode. The App builder limits the lock file
to 1 MiB and verifies its SHA-256 again after both slices compile. Repository
attack fixtures prove that an out-of-date lock is rejected without mutation,
while ordinary automatic resolution would rewrite the same offline fixture.

Product-version identity is validated before it reaches either the App or this
document. The shared repository validator accepts one owner-controlled,
single-link, non-writable `VERSION` file containing exactly a canonical numeric
`major.minor.patch` line. The same value must feed both Apple bundle version
fields, archive/Cask/Appcast metadata, the SBOM namespace, and downloaded
Release verification. Missing input never falls back to an older version, and
prerelease suffixes remain disabled until a distinct Apple/Sparkle build-number
policy is reviewed.

The Release pipeline provides four complementary checks:

1. `SHA256SUMS` detects downloaded-file corruption or substitution relative to
   the published inventory;
2. the repository-owned offline verifier binds the SPDX document version and
   source revision to the Cask, Appcast, tag and downloaded binary aliases,
   and independently requires all nine brand packages, every source/bundled
   asset and notice hash, upstream hash/transform, review field, package URL where asserted, and
   `CONTAINS` relationship;
3. GitHub build provenance binds each asset, including the SBOM, to the tagged
   workflow; and
4. a separate GitHub Sigstore SBOM attestation binds the same SPDX document to
   both DMG and ZIP aliases.

After publication, run the complete read-only verifier from a repository
checkout:

```sh
./scripts/release/verify-published-release.sh vX.Y.Z
```

It downloads exactly eight assets and requires SLSA provenance for all eight,
plus the SPDX predicate for both DMG and ZIP aliases. Public v0.3.0 predates
the complete-asset contract and is expected to fail with a precise legacy
Release error. The first subsequent complete tag is not accepted until this
command succeeds and the previous notarized version completes a signed
old-to-new Sparkle update.

## Non-goals

- The SBOM does not prove that a dependency is vulnerability-free.
- It does not replace source/license review or third-party notices.
- Listing a brand asset does not grant trademark rights or imply affiliation
  or endorsement; the mark is used nominatively to identify the integration.
- It does not claim that every resolved package is a direct dependency; the
  lock file includes the complete transitive SwiftPM resolution.
- A locally generated JSON file is not production evidence until its Release
  checksum and repository-bound Sigstore attestations verify.
